## 1. 共通の決まり

- URL は `/api` で始まる。開発中のあて先は `http://127.0.0.1:8080`。画面からは、Vite の中継（proxy）を通して `/api/...` で呼ぶ（[技術スタック](技術スタック.md) の2章）。
- やりとりは JSON（文字コードは UTF-8）。
- ボードごとのものは、URL もボードの下に置く（例：`/api/boards/{boardId}/tasks`）。タスク1件のように番号だけで決まるものは、短い URL にする（例：`/api/tasks/{taskId}`）。

### 1.1 返事の共通の包み

成功でも失敗でも、次の4つの項目で返す。

| 項目 | 成功のとき | 失敗のとき |
|---|---|---|
| `success` | `true` | `false` |
| `data` | 返すデータ | `null` |
| `error` | `null` | `{ "code": "…", "message": "…" }` |
| `meta` | 今は使わず `null` | `null` |

### 1.2 値の書き方

| 項目 | 書き方 |
|---|---|
| `status`（カラム） | `"todo"`（未着手）・`"doing"`（作業中）・`"done"`（完了） |
| `priority`（優先度） | `"high"`・`"medium"`・`"low"`。なしは `null` |
| `color`（ラベルの色） | `"green"`・`"yellow"`・`"orange"`・`"red"`・`"purple"`・`"blue"` |
| `dueDate`（期限日） | `"2026-11-10"` の形の文字列（時刻なし）。なしは `null` |
| `description`（説明） | 文字列。なしは `null` |
| ラベルの `name` | 文字列。名前なしは `""`（空の文字） |

### 1.3 エラーのとき

画面には分かりやすい日本語だけを出し、SQL やプログラムの内部情報は出さない。詳しい内容はサーバーのログにだけ残す（N-17）。

| 場面 | 状態コード | `error.code` | `error.message` |
|---|---|---|---|
| タスクがない | 404 | `TASK_NOT_FOUND` | タスクが見つかりません |
| ボードがない | 404 | `BOARD_NOT_FOUND` | ボードが見つかりません |
| 送った中身のチェックに通らない | 400 | `VALIDATION_ERROR` | 何が正しくないかの文（3.4） |
| 送った中身が読み取れない（空・壊れた JSON・日付の形が違う） | 400 | `INVALID_BODY` | 送られた内容の形が正しくありません |
| ボードのタスクが上限（200件） | 409 | `TASK_LIMIT_REACHED` | これ以上タスクを作成できません |
| 同じボードへの作成が重なり、5秒待っても順番が来ない | 503 | `BUSY` | 混み合っています。少し待ってからもう一度お試しください |
| URL の番号が数字でない | 400 | `INVALID_ID` | 番号の形が正しくありません |
| ない URL | 404 | `NOT_FOUND` | 指定された URL は見つかりません |
| その URL で使えないメソッド | 405 | `METHOD_NOT_ALLOWED` | この URL では使えない操作です |
| 予想外のエラー | 500 | `INTERNAL_ERROR` | サーバーでエラーが起きました |

## 2. API の一覧

| メソッド | URL | すること | 関係する機能 |
|---|---|---|---|
| GET | `/api/boards` | ボードの一覧 | F-01・F-02 |
| GET | `/api/boards/{boardId}/tasks` | 1つのボードのタスク全件（ラベル付き） | F-01・F-51 |
| GET | `/api/tasks/{taskId}` | タスク1件（ラベル付き） | F-11 |
| POST | `/api/boards/{boardId}/tasks` | タスクを作る | F-10 |
| GET | `/api/boards/{boardId}/labels` | 1つのボードのラベル全部 | F-10・F-40 |

## 3. それぞれの API

### 3.1 GET `/api/boards`：ボードの一覧

- タブの並び順（`position` の小さい順）で返す。

```json
{ "success": true,
  "data": [ { "id": 1, "name": "仕事", "position": 0 },
            { "id": 2, "name": "プライベート", "position": 1 } ],
  "error": null, "meta": null }
```

### 3.2 GET `/api/boards/{boardId}/tasks`：1つのボードのタスク全件

- 並び順：**未着手 → 作業中 → 完了**の順。同じカラムの中は `position` の小さい順。
- ラベルは、タスクごとに番号の小さい順。
- ボードはあるがタスクが0件のときは、エラーにせず `"data": []` を返す。
- ボードがないときは 404（`BOARD_NOT_FOUND`）。

```json
{ "success": true,
  "data": [ { "id": 1, "boardId": 1, "status": "todo", "position": 0,
              "title": "経費の精算を出す", "description": null,
              "completed": false, "priority": "high", "dueDate": "2026-11-07",
              "labels": [ { "id": 1, "name": "緊急", "color": "red" },
                          { "id": 2, "name": "請求", "color": "yellow" } ] } ],
  "error": null, "meta": null }
```

| 項目 | 中身 |
|---|---|
| `id` | タスクの番号 |
| `boardId` | 所属するボードの番号 |
| `status` | どのカラムにあるか（1.2） |
| `position` | カラムの中の表示順（0 から） |
| `title` | タイトル |
| `description` | 説明（なしは `null`） |
| `completed` | 完了マーク（✓）の有無 |
| `priority` | 優先度（なしは `null`） |
| `dueDate` | 期限日（なしは `null`） |
| `labels` | 付いているラベル（`id`・`name`・`color`）の一覧 |

### 3.3 GET `/api/tasks/{taskId}`：タスク1件

- `data` に、3.2 と同じ形のタスクを1つ入れて返す。
- タスクがないときは 404（`TASK_NOT_FOUND`）。番号が数字でないときは 400（`INVALID_ID`）。

```json
{ "success": false, "data": null,
  "error": { "code": "TASK_NOT_FOUND", "message": "タスクが見つかりません" },
  "meta": null }
```

### 3.4 POST `/api/boards/{boardId}/tasks`：タスクを作る

- 作成モーダル（S-02）の「作成」で呼ぶ。全部の項目を1回で送る。
- 新しいタスクは、選んだカラムの**一番下**に入る（R-01）。`position` はサーバーが「そのカラムの最大値＋1」で決める（空のカラムなら 0）。
- `id` はデータベースが自動で付ける（`tasks` の `GENERATED BY DEFAULT AS IDENTITY`）。消した番号は使い回さない。
- `id`・`position`・`completed` は送っても使わない。新しいタスクはチェックなし（`completed: false`）。
- 成功したら **201** と、3.2 と同じ形の作ったタスクを返す。

送るもの：

```json
{ "title": "資料を印刷する", "description": null, "status": "todo",
  "priority": "high", "dueDate": "2026-11-25", "labelIds": [3, 4] }
```

| 項目 | 必須 | ルール | 正しくないときの `error.message`（400 `VALIDATION_ERROR`） |
|---|---|---|---|
| `title` | ○ | 前後の空白を取って、1〜100文字（R-03, R-05, R-06） | タイトルを入力してください／タイトルは100文字までです／使えない文字が含まれています |
| `description` | | 前後の空白を取って、1000文字まで。空白だけ・`null` は「説明なし」 | 説明は1000文字までです／使えない文字が含まれています |
| `status` | ○ | `todo`・`doing`・`done` | カラムを選んでください／カラムの値が正しくありません |
| `priority` | | `high`・`medium`・`low`・`null` | 優先度の値が正しくありません |
| `dueDate` | | `"2026-11-25"` の形・`null`。1900-01-01〜9999-12-31。過去の日付も可（R-11） | 期限の日付が正しくありません（形が違うと 400 `INVALID_BODY`） |
| `labelIds` | | 同じボードのラベルの番号を20個まで（R-17）。同じ番号は1つにまとめる。`null`・`[]` はラベルなし | 選べないラベルが含まれています |

- 文字数は、絵文字も1文字として数える（データベースと同じ数え方）。
- NUL 文字（`\u0000`）はデータベースに入れられないため、使えない文字として 400 にする。
- チェックの順番：①送った中身 → ②ボードがあるか → ③件数の上限 → ④ラベル。たとえば、ないボードに空のタイトルを送ると、①の 400 が先に返る。
- ほかのエラー：ボードがない 404（`BOARD_NOT_FOUND`）、ボードのタスクが200件 409（`TASK_LIMIT_REACHED`、R-29）。
- 同じボードに同時に作られても、上限のすり抜けや順番の重なりが起きないよう、ボードの行をロックしてから「件数の確認 → 順番の計算 → 保存」を1つのトランザクションで行う。ロックは最大5秒待ち、待ちきれなければ 503（`BUSY`）。
- **これから作る書き込み（更新・削除・並び替え・ラベルの削除・毎日のリセット）も、タスクの件数や `position` を変えるときは、同じボードのロックを先に取る。** データベースには `position` の重なりを止める決まり（UNIQUE）がないため、ロックで順番を守る。

### 3.5 GET `/api/boards/{boardId}/labels`：1つのボードのラベル全部

- 作成モーダルのラベル欄に出すため、タスクに付いていないラベルも含めて、番号の小さい順で返す。
- ボードがないときは 404（`BOARD_NOT_FOUND`）。

```json
{ "success": true,
  "data": [ { "id": 1, "name": "緊急", "color": "red" },
            { "id": 2, "name": "請求", "color": "yellow" } ],
  "error": null, "meta": null }
```

- データを消して見本データに戻す処理（毎日のリセット、F-55）は、まだ作っていない。

## 5. 作ったデータがデータベースに入ったかの確かめ方

タスクを作ったあと（3.4）、データが本当にデータベースに入ったかを、**見るだけの命令**で確かめる手順。どのタスクにも使えるよう、「いちばん新しく作ったタスク」を見る形にしている。

### 5.1 守ること

- 使うのは `SELECT` と `SHOW` だけ。`INSERT`・`UPDATE`・`DELETE` など、データを変える命令は使わない。
- 読み取り専用の設定（`default_transaction_read_only=on`）でつなぐ。もし変える命令を流しても、データベースが断る。
- パスワードなどの秘密は表示しない。`.env` は開かず、コンテナの中の設定を使ってつなぐ。
- 確かめるためにサーバーを起動したときは、終わったら API サーバーと画面を止める。データベースは動かしたままでよい。

### 5.2 準備

1. データベースが動いているかを見る。`taskboard-db-1` が `(healthy)` なら準備ができている。

   ```bash
   docker compose ps
   ```

2. 次の形でつなぐ（リポジトリ直下で実行する）。`"ここに SELECT 文"` を、下の手順の SQL に置き換える。`-c "…"` を並べると、続けて流せる。

   ```bash
   docker compose exec -T db sh -c 'PGOPTIONS="-c default_transaction_read_only=on" psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "ここに SELECT 文"'
   ```

3. 最初に、書き込み禁止になっているかを確かめる。`on` と出れば正しい。

   ```sql
   SHOW default_transaction_read_only;
   ```

### 5.3 手順

**① 作る前の数を控える**（作ったあとと比べるため）

```sql
SELECT COUNT(*) AS 件数, MAX(id) AS id_最大値 FROM tasks;
```

**② tasks（タスク本体）を見る**

```sql
SELECT id, board_id, status, position, title, description,
       is_completed, priority, due_date, created_at
FROM tasks ORDER BY id DESC LIMIT 1;
```

- 画面で入れたタイトル・カラム・優先度・期限・説明と同じか。
- `is_completed` が `f`（チェックなし）か。`created_at` が作った時刻か。

**③ task_labels（ラベルの結び付き）を見る**

```sql
SELECT tl.task_id, l.id AS label_id, l.name, l.color
FROM task_labels tl JOIN labels l ON l.id = tl.label_id
WHERE tl.task_id = (SELECT MAX(id) FROM tasks)
ORDER BY l.id;
```

- 画面で選んだラベルが、選んだ数だけ出るか。ラベルを選ばなかったときは 0 行が正しい。

別のボードのラベルが混ざっていないか（**0 行なら正しい**）：

```sql
SELECT tl.task_id, l.name, l.board_id AS ラベルのボード, t.board_id AS タスクのボード
FROM task_labels tl
JOIN labels l ON l.id = tl.label_id
JOIN tasks t ON t.id = tl.task_id
WHERE l.board_id <> t.board_id;
```

**④ カラムの一番下に入ったか（R-01）**

```sql
SELECT id, position, title FROM tasks
WHERE board_id = (SELECT board_id FROM tasks WHERE id = (SELECT MAX(id) FROM tasks))
  AND status = (SELECT status FROM tasks WHERE id = (SELECT MAX(id) FROM tasks))
ORDER BY position;
```

- 新しいタスクが一番下（`position` が最大）にあり、ほかのタスクと番号が重なっていないか。

**⑤ 画面を再読み込みしても残っているか**

1. 画面（`http://localhost:5173`）でタスクを作り、小窓が閉じて、選んだカラムの一番下にカードが出ることを見る。
2. ブラウザを再読み込みする（Mac は `⌘ + R`）。
3. 同じボード・同じカラムの一番下に、同じカードが残っているかを見る。カラムの件数（例：「作業中 (4)」）も、作った直後と同じか。
4. 念のため、`http://127.0.0.1:8080/api/tasks/{番号}` を開くと、データベースから読み直した中身が JSON で出る（3.3）。

再読み込みで残っていれば、画面の中の一時的な表示ではなく、データベースから読み直した結果だと言える。

**⑥ 作ったあとの数を確かめる**

①と同じ SQL を流し、件数が 1 増え、`id_最大値` が新しいタスクの番号になっているかを見る。
