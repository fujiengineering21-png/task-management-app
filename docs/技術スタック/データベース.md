## 1. 使っている技術

| 役割 | 技術 | 決めた版 | 入っている版 | 最新版 | 選んだ理由 |
|---|---|---|---|---|---|
| データベース | PostgreSQL | 17 | 17.11（Docker イメージ `postgres:17-alpine`。2026-10-21 に作られたもの） | 17 系：17.12 🔼／いちばん新しいのは 18.7 ⏸ | コースの指定。17 は2029年11月までサポートがある。17.12 への上げ方は 1.3、18 にしない理由は 1.1 |
| 開発中の動かし方 | Docker Desktop ＋ Docker Compose | — | Docker 29.9.2・Compose 5.6.1 | Docker Desktop の自動更新に任せる | 1つのコマンドで同じデータベースを用意できる。PC に直接入れた PostgreSQL（別のプロジェクトで使用中）とぶつからない（Q29） |
| テーブルの作成・変更 | Flyway（Spring Boot が版を決める） | Boot に合わせる | 12.4.0 | — | テーブルの作り方を SQL ファイルで残し、何度でも同じ手順で作り直せる（N-28） |
| Java からの接続 | PostgreSQL JDBC ドライバ（Spring Boot が版を決める） | Boot に合わせる | 42.7.14 | — | [バックエンド](バックエンド.md) |
| 公開先のデータベース | Neon Free（PostgreSQL 17） | 17 | ⏳ | — | 無料で期限がない。公開のステップで作る（[技術スタック](../技術スタック.md) の5章） |

### 1.1 PostgreSQL を 18 にしない理由

- 自分の PC（Docker）・公開先（Neon）・自動テスト（GitHub Actions）の3か所を、同じ **17** にそろえるため。場所によって版が違うと、「手元では動くのに公開先で動かない」が起きやすい。
- 17 は2029年11月までサポートがあり、課題の期間には十分。

### 1.2 `alpine` の版を選んだ理由

- `alpine` は小さい版のイメージで、ダウンロードが速く、容量も少ない。
- 文字の並べ替えのルール（照合順序）が通常の版と違うことがあるが、このアプリは文字列で並べ替えないので、日本語でも問題ない。

### 1.3 17 系の中で版を上げる（17.11 → 17.12 など）

- `compose.yaml` には `17-alpine` としか書いていないので、**手元のイメージは、最初にダウンロードした時点の版のまま**になる。自動では新しくならない。
- 新しい 17.x にするときは、リポジトリ直下で `docker compose pull` → `docker compose up -d` を実行する。17 の中の小さな更新なので、データ（ボリューム `db-data`）はそのまま使える。
- 18 のような大きな版に上げるときは、データの移し替えが必要になる。この手順では上げない。

### 1.4 版の確かめ方

| 確かめたいもの | コマンド（リポジトリ直下） |
|---|---|
| 手元のイメージの版 | `docker image inspect postgres:17-alpine --format '{{range .Config.Env}}{{println .}}{{end}}' \| grep PG_VERSION` |
| 動いているデータベースの版 | `docker compose exec db psql -U taskboard -d taskboard_dev -c 'select version();'` |

- PC には、別のプロジェクト用に Homebrew の PostgreSQL 17（17.10、5432番）も入っている。`psql --version` で出る版はこちらなので、TaskBoard のデータベースの版とは別物。

## 2. 開発用のデータベース（`compose.yaml`）

| 項目 | 値 | 意味 |
|---|---|---|
| サービス名 | `db` | `docker compose exec db …` のように使う |
| ポート | **5433**（PC 側）→ 5432（コンテナの中） | 5432 は、PC に直接入れた PostgreSQL（Homebrew・別のプロジェクト用）が使っているので避けた。番号は変えない（[CLAUDE.md](../../CLAUDE.md) のルール6） |
| 待ち受ける場所 | `127.0.0.1` | この PC からだけ接続できる。同じ Wi-Fi の他の機器からはつながらない |
| データベース名 | `taskboard_dev` | 開発用。テスト用の `taskboard_test` は、データベースを使うテストを書くときに作る（N-08） |
| データの置き場所 | Docker のボリューム `db-data` | コンテナを作り直してもデータは消えない |
| 起動の確認 | `pg_isready`（5秒ごと） | 接続を受け付けられる状態になったかを確かめる |

- 名前・ユーザー名・パスワード・ポートは、リポジトリ直下の `.env` から読む（見本は `.env.example`）。`.env` がないと、起動のときにエラーで知らせる。
- `.env` のパスワードは、データベースを**最初に作ったときだけ**使われる。あとで変えると接続できなくなる。

## 3. テーブルの作り方（Flyway）

- テーブルは `backend/src/main/resources/db/migration/` の SQL ファイルで作る。APIサーバーの起動のときに、まだ実行していない SQL だけを Flyway が実行する。
- 今あるのは `V1__create_tables.sql`（boards・tasks・labels・task_labels の4テーブル、Q19）。
- **一度実行した SQL は書き換えない**：書き換えると、Flyway が食い違いに気づいて起動に失敗する。テーブルを変えるときは `V2__〇〇.sql` を新しく足す。
- JPA にはテーブルを作らせない（`ddl-auto=validate`。[バックエンド](バックエンド.md) の3章）。

## 4. よく使うコマンド

リポジトリ直下で実行する。先に Docker Desktop を開いておく。

| コマンド | すること |
|---|---|
| `docker compose up -d` | データベースを起動する（裏で動かし続ける） |
| `docker compose ps` | 動いているかを確かめる（`healthy` なら準備完了） |
| `docker compose stop` | 止める（データは残る） |
| `docker compose exec db psql -U taskboard -d taskboard_dev` | データベースの中に入る。`\dt` でテーブル一覧、`\q` で終わる |

- ふつうに `psql` を実行すると、Homebrew の PostgreSQL（5432番・別のプロジェクト用）につながるので注意。そちらは止めたり変更したりしない。
- PC を再起動したあとは、Docker Desktop を開いて `docker compose up -d` からやり直す。

## 5. うまく動かないとき

| 出るエラー・状態 | 原因 | 直し方 |
|---|---|---|
| `127.0.0.1:5433 への接続が拒絶されました` | データベースが動いていない | Docker Desktop を開き、`docker compose up -d` |
| `docker compose up` で「.env がありません」と出る | `.env` を作っていない | リポジトリ直下で `cp .env.example .env` をして、パスワードを自分だけの値に変える |
| `password authentication failed` | データベースを作ったあとで `.env` のパスワードを変えた | `.env` を元の値に戻す |
| `failed to connect to the docker API` | Docker Desktop が起動していない | Docker Desktop を開いてから、もう一度実行する |
| APIサーバーの health が `{"status":"DOWN"}` | 起動したあとでデータベースが止まった | `docker compose up -d`。戻るまで30秒ほどかかることがある |
